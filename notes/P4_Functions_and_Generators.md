### 18.1 PART opener 承接、有限阶段地图与本质模型

本章真正目标不是记住 `def` 和 `return` 的拼写，而是建立一条可以逐节点解释的时间线：

```tex
源码中的 def
→ 解析与编译形成代码相关产物
→ 运行到 def 语句
→ 创建函数对象并绑定名字
→ 求值调用表达式的实参
→ 建立本次调用的局部绑定并执行函数体
→ 正常 return 或异常退出
→ 调用表达式产生结果或向外传播异常
→ 调用方后续语句才可能继续
```

有限主线只覆盖六层：

| 层次 | 必须回答的问题 | 本章结论 |
| --- | --- | --- |
| 定义 | 执行 `def` 是否会执行函数体？ | 不会；它创建函数对象并绑定定义名称 |
| 对象 | `function` 与 `function()` 是否相同？ | 前者取得函数对象，后者发起调用并形成调用结果或异常 |
| 调用 | 实参如何进入函数？ | 先求值，再把对象引用绑定给本次调用的形参局部名字；基本调用不自动复制对象 |
| 退出 | 函数怎样结束？ | 显式 `return`、裸 `return`、运行到末尾，或异常退出 |
| 合同 | 调用者能观察到什么？ | 返回对象、传入对象的修改、输出流写入、外部状态变化与异常是不同通道 |
| 证据 | 文档、签名、注解和一次运行能证明什么？ | 各自只提供有限证据，不能单独等同于完整运行合同 |

本章的必学核心是上表；必要补救集中在四个旧风险：

1. `function` 不是 `function()`；
2. 形参绑定不是“把实参对象复制进函数”；
3. `print()`、原地修改和持久化不是 `return`；
4. `callable()`、签名绑定成功或注解存在，都不保证真实调用成功。

函数属性的完整目录、栈帧、字节码、闭包、高阶函数、完整 LEGB、完整参数规则和生成器都不是本章必学范围。它们即使曾被追问，也只能作为解释当前模型所需的有限拓展，不能改变主线完成标准。

### 18.2 `def` 执行：函数对象、名字绑定、别名与重新定义

遇到函数定义时，要分清三个时间点：源码被解析和编译、控制流执行 `def` 语句、未来某次调用执行函数体。最基本的观察如下：

```python
events = []

def record():
    events.append("body")
    return "done"

print(events)       # []：定义时函数体没有运行
alias = record      # 同一个函数对象的新引用
print(alias is record)  # True
print(record())     # done：这里才执行函数体
print(events)       # ['body']
```

应知应会：

- `def` 是可执行语句。控制流运行到它时，Python 创建函数对象，并让定义名称绑定到该对象。
- `alias = record` 复制的是对象引用，不是函数体，也不创建新的函数对象。
- 把函数对象放入列表、字典或作为另一个名字的值，仍然只是建立额外引用。
- `record` 是函数对象；`record()` 是调用表达式。调用结果可能与函数对象完全不同，也可能根本没有正常结果而是传播异常。
- 函数体内的副作用、异常和返回路径只会在实际调用且执行到对应语句时发生。

同名的第二个 `def` 会创建新的函数对象，再改变该名字的绑定；它不会“就地修改”旧函数：

```python
def label():
    return "v1"

old = label

def label():
    return "v2"

print(old(), label())                 # v1 v2
print(old is label)                   # False
print(old.__name__ == label.__name__) # True
```

这里的关键边界是：

- `old is not label` 说明两个名字当前指向不同函数对象；
- `old.__name__ == label.__name__` 只说明两个对象记录了相同的定义名称字符串；
- 元数据相等不推出对象身份相同；
- 旧函数没有被修改或销毁，只要 `old` 等引用仍存在，它就仍然可达、可调用。

此前作答已经准确抓住这一点。唯一需要固定的书写细节是特殊属性名应写成 `__name__`，而不是被 Markdown 加粗语法误显示成 `**name**`。

### 18.3 调用边界：实参对象、形参局部绑定、修改与重新绑定

一次基本调用可以先用下面的有限模型理解：

```tex
求值实参表达式
→ 把所得对象引用绑定给本次调用的形参局部名字
→ 执行函数体
```

这不等于“按值复制整个对象”，也不等于“把调用方变量本身传进去”。函数收到的是对象，形参是本次调用中的局部名字。于是要继续沿用 P3 的对象模型来区分修改和重新绑定：

```python
def update(items):
    original = items
    items.append("body")  # 修改共享列表对象
    items = ["local"]     # 只重新绑定局部名字
    return original

records = ["caller"]
result = update(records)

print(records)          # ['caller', 'body']
print(result)           # ['caller', 'body']
print(result is records)  # True
```

精确解释：

- `items.append("body")` 作用于形参与调用方名字共同引用的列表对象，因此调用后可从 `records` 观察到修改。
- `items = ["local"]` 只是让本次调用中的局部名字改指向新列表，不会自动改变 `records` 的绑定。
- `original` 在重新绑定前保存了原列表引用，因此返回的仍是原列表，`result is records` 为真。
- “函数内改了变量”太含糊。必须说明是**修改了某个对象**，还是**重新绑定了某个名字**。
- 对不可变对象执行产生新值的运算，通常表现为得到另一个结果并重新绑定名字；不要把它描述为原对象被原地改变。

工程上，若函数会修改调用者传入的可变对象，应在名称、文档或接口设计中明确表达；若希望数据变换更易组合和测试，优先返回明确结果，并谨慎决定是否同时承担原地修改。完整参数匹配规则属于 C18，本章只保留“实参求值 + 本次调用局部绑定”的基础模型。

### 18.4 函数退出：返回路径、不可达代码、异常与调用方赋值

正常退出和异常退出必须分开：

| 函数路径 | 调用表达式的正常结果 | 调用方后续行为 |
| --- | --- | --- |
| `return value` | `value` 求值得到的对象 | 可继续执行并用于赋值、传参或组合 |
| 裸 `return` | `None` | 正常继续 |
| 执行到函数体末尾 | `None` | 正常继续 |
| 抛出且未在函数内处理的异常 | 没有正常返回值 | 异常向外传播，正常路径被中断 |

重要边界：

- `return` 一旦执行，本次调用立即正常结束；同一路径中它后面的语句不可达。
- 裸 `return` 与自然落到末尾都正常返回 `None`，但这不意味着异常退出也“返回了 `None`”。
- 调用方赋值如 `result = risky()`，只有在右侧调用正常产生结果后才完成名字绑定。
- 若右侧传播异常，赋值语句没有完成；名字可能保持旧绑定，也可能在此前从未绑定。
- 异常会改变正常控制流，可能继续向外传播、展开调用栈，并触发适用的 `finally` 清理；不能把它缩写成“只改变控制流”。
- Python 不会因为异常自动回滚此前已经完成的对象修改、输出或外部写入。

```python
events = []
result = "previous"

def risky(target):
    target.append("entered")
    raise RuntimeError("boom")

try:
    result = risky(events)
except RuntimeError:
    events.append("caught")

print(result)  # previous
print(events)  # ['entered', 'caught']
```

这里 `"entered"` 不会因异常消失，因为 `append()` 已经完成了对共享列表的原地修改；`result` 保持旧值，是因为包含调用的赋值语句没有完成。此前对此题的推理是准确的。更精确的工程结论是：如果操作包含多个副作用步骤，就必须单独设计验证、补偿或事务边界，不能把异常机制误当成自动撤销机制。

### 18.5 函数合同：返回对象、参数修改、输出流与外部效果

评价一个函数时，至少分开观察四种通道：

```tex
函数合同
= 返回对象
+ 对传入对象的可见修改
+ 输出流写入
+ 文件、网络、数据库等外部状态变化
+ 可能传播的异常
```

它们之间不能相互替代：

| 现象 | 能直接证明什么 | 不能直接证明什么 |
| --- | --- | --- |
| `return report` | 调用表达式正常得到 `report` 所指对象 | 已经显示或保存 |
| `print(report)` | 向指定输出接收者发起格式化写入；`print()` 自身返回 `None` | 业务结果就是 `None`；内容已经持久化 |
| `target.append(x)` | 目标列表对象已被原地修改 | 函数返回了该列表 |
| `stream.write(text)` | 向该接收者发起写入；返回值通常是写入字符数 | 接收者一定是磁盘文件或用户一定看见内容 |
| `StringIO.getvalue()` | 当前内存文本缓冲区包含什么 | 内容已落盘、已刷新到设备或具有事务保证 |

本章最重要的工程习惯是让核心计算和边界效果可分离：

```python
def build_report(records):
    return {"count": len(records)}

def print_report(report, stream):
    print(f"count={report['count']}", file=stream)
```

这样可以分别验证结构化返回值与具体输出接收者的状态。`StringIO` 很适合做内存中的可观察接收者，但它只证明缓冲区状态；若换成终端、磁盘文件、网络包装器或自定义对象，刷新、持久化、失败方式和位置语义都由具体接收者决定。

阶段测验唯一扣分点正位于这里：曾把 `StringIO` 上观察到的“内容和位置变化”推广成所有 `print(..., file=...)` 兼容对象的通用保证。精确修复是：

1. 函数或 `print()` 负责**发起若干写入操作**；
2. 接收对象的具体协议与实现决定每次写入产生什么效果；
3. 可读内容、当前位置、刷新、持久化和可见性都不是抽象“可写对象”自动承诺的统一结论；
4. 多次 `write()` 不构成原子事务，中途失败时可能已留下部分效果。

因此，工程合同应明确：谁负责计算，谁负责展示或保存，调用是否修改输入，失败时可能留下哪些部分效果，以及哪些职责明确不属于该函数。

### 18.6 函数元数据、签名、注解与有限证据

“元数据”是对描述对象之信息的用途分类，不等于“函数对象所有前导和尾随双下划线属性的值”。许多双下划线属性属于 Python 数据模型接口；其中有些可视为描述函数的元数据，有些承担运行协议或实现联系。不要用拼写形式替代语义分类。

本章涉及的典型属性可这样理解：

| 属性 | 主要意义 | 形成或求值时机的关键点 |
| --- | --- | --- |
| `__name__` / `__qualname__` | 定义名称及限定名称 | 相关信息由编译产物提供，执行 `def` 创建函数对象时关联到对象 |
| `__doc__` | 函数文档字符串或 `None` | 文档字符串作为函数源码结构的一部分被编译；创建函数对象时成为其文档属性 |
| `__code__` | 已编译的函数体代码对象 | 在外围代码编译过程中形成；执行 `def` 时连接到新函数对象 |
| `__defaults__` | 已求值的位置参数默认值元组或 `None` | 默认值表达式在每次执行 `def` 时求值，然后交给新函数对象 |
| `__annotations__` | 注解映射 | 时机依 Python 版本与注解机制而异；不能笼统说所有注解都在 `def` 时立即求值 |

必须分开“编译源码”和“执行定义”：

```python
def sample(value: str, suffix="x") -> str:
    """Return a labeled value."""
    return value.strip() + suffix
```

- 解析和编译会检查语法、形成函数体代码对象以及定义所需的常量和名称信息；函数体不会因此执行。
- 函数体本身的语法错误、重复参数等静态非法结构会在编译阶段阻止这段代码正常产生可执行结果，即使未来从不调用该函数。
- 控制流真正执行 `def` 时才创建函数对象，并求值默认值表达式。默认值表达式此时若触发 `NameError` 等异常，本次 `def` 就不会完成相应名称绑定。
- 函数体里引用的普通名字通常不要求定义时已经有值；只要语法可编译，可能直到调用并执行到该路径时才发生 `NameError`。
- 在本章当前解释器 Python 3.14.5 的默认注解语义下，函数注解采用延迟求值机制：定义时可先建立延迟求值入口，随后访问 `__annotations__` 等操作才可能触发注解表达式求值。这是版本相关事实，不能倒推旧版本或不同注解配置的行为。

文档字符串、签名和注解提供的是不同维度的证据：

- `callable(obj)` 只说明对象可被调用，不说明某组实参会成功，更不说明业务结果正确。
- `inspect.signature(func)` 显示当前可见的调用形状，是运行时内省证据。
- `signature.bind(...)` 只检查这组参数能否按签名形状绑定；它不会执行函数体，也不会验证业务语义或注解类型。
- 注解表达设计意图，Python 默认不会仅因 `value: str` 就阻止传入整数。
- 文档字符串说明作者声明的用途和约定，不是运行成功证据。
- 一次成功运行只证明该具体输入和环境下的观察结果，不能独自证明所有路径的完整合同。

例如，`sample(404)` 的参数形状可以绑定，注解也仍可读取，但真实调用会在求值 `value.strip` 时确定地触发 `AttributeError`：失败点是**属性查找**，甚至还没有进入 `strip()` 方法调用。对给定代码、输入和 Python 3.14.5 环境，这个异常类型是确定事实；“实验范围有限”不应被误写成该次结果本身“不确定”。

本节来自学习中的高质量追问，属于可选拓展而不是当前目标修复：它加深了定义时间线与证据边界，却不把字节码、描述器或完整反射协议加入 C16 必学范围。

### 18.8 本阶段的理解轨迹、追问与修正规则

本章的学习表现不是从“不会写函数”起步，而是把已有对象模型提升成更精确的函数模型。几次关键作答如下。

#### 1. 同名 `def`、旧引用与元数据相等

你准确判断第二个 `def` 改变的是全局名字 `label` 的绑定，旧函数对象没有被修改，并因 `old` 的引用继续存在；也进一步注意到 `old is not label` 与 `old.__name__ == label.__name__` 可以同时为真。

应保留的最小结论是：**名字绑定、对象身份和元数据值属于不同观察层。** “名称相同”不是“对象相同”的证据。

#### 2. 共享列表修改与形参局部重新绑定

你准确区分了 `items.append("body")` 对共享列表的原地修改，以及 `items = ["local"]` 对局部名字的重新绑定；也正确判断返回 `original` 后 `result is records` 为真。

应保留的最小结论是：**函数调用建立新的局部名字绑定，但不因此复制实参对象；可见性取决于操作落在对象上还是名字上。**

#### 3. 元数据时机、编译产物与运行时函数对象

你追问了函数元数据是否等同于双下划线属性、各属性何时确定、函数体源码编译时发生什么，以及哪些错误会在编译期暴露。这不是主线缺口，而是从“`def` 不执行函数体”自然延伸出的高质量可选拓展。

应保留的修复是：不要寻找一个覆盖所有属性的单一“确定时刻”。源码解析和编译、执行 `def`、延迟求值某些注解、调用函数体是不同阶段；`__code__`、默认值和 Python 3.14 的注解机制分别跨在不同节点上。

#### 4. 异常前副作用与未完成的调用方赋值

你准确解释了异常前已执行的 `append()` 不会消失，以及 `result = risky(...)` 因右侧调用异常退出而没有完成，故 `result` 保持旧绑定。

应保留的精度修复是：异常不只是一个抽象的“跳转”；它会中断正常路径、传播并可能展开栈和执行清理，但不会自动为已经完成的副作用提供事务回滚。

本章没有出现需要重新教学的重复概念错误。P3 曾需重点防守的 `==` 与 `is`、修改与重新绑定、输出与返回、注解与强制检查等边界，在 C16 作答中总体稳定。后续仍应警惕的是**表述泛化过快**：从一个具体接收者、一次实验或一个属性观察，不要直接推出更广的接口保证。


此外，批改中还固定了若干不扣分但值得保留的精度修正：

1. 字符串方法返回结果且不原地修改原字符串，但不能普遍承诺结果一定具有全新的对象身份；“新字符串”应理解为规范化结果，而不是 `is not` 保证。
2. 异常中断正常路径且可能传播、展开栈并执行 `finally`；“不会自动回滚此前效果”比“异常只影响控制流”更完整。

6. `inspect.signature()` 是当前运行时内省，注解表达设计意图，`Signature.bind()` 只提供调用形状证据；三者不能混成“类型检查通过”。

8. 某实现偶然接受更多鸭子类型对象，不会自动扩大正式业务合同；本题合同仍是 `str` 及字符串列表。
9. `callable()`、签名、绑定、文档、注解或一次成功运行，任意单项都不是完整合同证明。
10. 多次写入可能留下部分效果；如果工程要求全有或全无，必须额外设计事务、临时结果或补偿策略。

### 18.10 工程应知应会、习惯、禁忌和技巧清单

#### 写函数前

- 用一句话写清函数的单一主要职责。
- 明确输入合同：对象应支持什么操作，业务上允许哪些值。
- 明确正常返回：返回对象的结构、各路径是否可能得到 `None`。
- 明确是否修改调用者提供的可变对象。
- 明确是否显示、写文件、访问网络或改变其他外部状态。
- 明确可能传播哪些异常，以及失败前是否可能留下部分效果。

#### 读函数时

- 先找定义名称绑定到哪个函数对象，不要看到 `def` 就假设函数体已经执行。
- 区分取函数对象、建立别名和发起调用三个动作。
- 沿每条控制流路径寻找 `return`、自然落尾和异常出口。
- 对每个赋值写清“哪个名字重新绑定到哪个对象”。
- 对每个方法调用写清“是否修改了哪个共享对象”。
- 分别记录返回值、输入修改、输出流状态和外部效果，不用一个“输出”概括全部。

#### 验证函数时

- 用 `is` 检查对象身份，用 `==` 检查值相等；不要互相替代。
- 为调用前、函数体、返回后建立最小事件时间线，定位执行顺序。
- 把调用结果保存在变量中，避免交互式显示掩盖真实返回值。
- 用 `StringIO` 验证内存输出时，同时写明它不能证明持久化。
- 用 `inspect.signature()` 和 `bind()` 检查形状时，再用真实调用验证函数体路径。
- 对成功路径、隐式 `None`、异常路径和异常前部分效果分别观察。

#### 禁忌

- 不把 `print()` 的屏幕文本称作函数返回值。
- 不把传入可变对象后的可见变化一律称作“返回了修改后的对象”。
- 不把形参局部重新绑定误写成调用方名字被改绑。
- 不把注解、文档或签名当成运行时类型强制与业务正确性证明。
- 不从一个具体输出接收者推导所有可写对象的统一刷新、位置、持久化或事务语义。
- 不因 PART opener 身份扩大到完整作用域、参数系统、高阶函数、生成器或额外 capstone。

#### 可复用技巧

- 核心函数优先返回结构化数据，显示和持久化放到边界层。
- 若函数承担副作用，让名称和文档显式表达，并记录部分失败语义。
- 用合同卡描述“职责 / 输入 / 返回 / 修改 / I/O / 异常 / 非职责”。
- 用导入保护隔离模块定义与脚本入口，避免仅导入就执行主流程。
- 用最小实验验证一个边界，并在结论旁同时写出“该实验没有证明什么”。

```tex
def 的核心：创建函数对象，并绑定名字；不是立即执行函数体。
调用的核心：求值实参，建立本次调用的局部绑定，再执行函数体。
```

### 19.1 有限阶段地图与名字解析本质模型

六个正式步骤组成一条有限路线：

| 步骤 | 必须回答的问题 | 稳定结论 |

| 模块全局与 `global` | 读取、修改对象和重绑模块名字有何区别？ | 读取模块名字通常无需声明；修改已找到对象不重绑名字；函数内重绑模块名字才需要 `global` |
| enclosing 与 `nonlocal` | 内层函数怎样改变外层函数绑定？ | `nonlocal` 指向词法上最近的已有外层函数绑定，不指向任意调用者或模块全局 |

| 命名空间观察与显式依赖 | 运行时映射能证明什么，配置应如何进入函数？ | `locals()` / `globals()` 只提供有边界的证据；影响计算的配置优先通过参数显式传入 |

贯穿全章的本质追踪链是：

```tex
先画源码中的词法嵌套
→ 判断操作是裸名字读取、简单名字绑定，还是对对象的操作
→ 确定名字类别和绑定目标
→ 沿本次真实控制流判断该绑定此刻是否已经建立
→ 读取时只走实际存在的词法层级并在首次命中后停止
→ 得到对象后，再判断是修改对象还是重新绑定名字
→ 最后记录正常结果、异常位置和异常前已完成的效果
```

必要补救不在于多背术语，而在于持续拒绝七种混写：局部命名空间不是调用方命名空间，也不是实参对象的复制；LEGB 读取和赋值目标不是同一条规则；对象可变性不决定名字类别；`UnboundLocalError` 不表示全局名字不存在；`global` / `nonlocal` 不改变对象归属；修改共享对象不自动要求作用域声明；命名空间映射也不是任意作用域的通用写回接口。

### 19.2 名字、绑定、命名空间、作用域与名字查找

这五个概念必须分层：

| 概念 | 精确含义 | 常见误写 |
| --- | --- | --- |
| 名字 | 源码中用于引用对象的标识符 | 把名字本身说成对象或带有固定类型的盒子 |
| 绑定 | 在某个命名空间中建立或替换“名字 → 对象”的关联 | 把绑定一律说成复制对象 |
| 命名空间 | 保存一组名字绑定的运行时环境 | 把不同函数调用的局部环境说成同一个字典 |
| 作用域 | 某段源码可直接使用未限定名字访问相应命名空间的文本区域 | 把作用域说成“装对象的容器” |
| 名字查找 | 求值一个未限定名字时，确定采用哪个已有绑定的过程 | 把查找规则直接套到所有赋值和属性访问上 |

```tex
名字不是对象。
对象不被“装进”作用域。
绑定存在于命名空间中。
作用域规定源码中哪些名字绑定可以被直接解析。
一个对象可以同时被多个命名空间中的多个名字引用。
```

每次函数调用都会建立属于该次调用的局部绑定环境；同一函数的两次调用不会共享一个局部命名空间。基本调用仍然不会因此复制实参对象：两个调用中的局部名字、模块名字或 enclosing 名字完全可能引用同一个对象。

还要先识别语法类别。`obj.attr` 中只有 `obj` 是未限定名字并使用名字解析；点号后的 `attr` 由对象属性协议查找。`records.append(x)` 先解析 `records` 再调用对象方法，通常不会重新绑定名字 `records`；`records[index] = x` 也不是重新绑定基础名字。LEGB 是普通未限定名字读取的模型，不是所有 Python 语境的万能规则。

### 19.3 LEGB、遮蔽、模块全局与 builtins 边界

LEGB 四个字母表示四类可能的查找来源，而不是每段代码都机械拥有四个实体层：

| 层 | 来源 | 关键边界 |
| --- | --- | --- |
| L — Local | 当前这次函数调用的局部绑定 | 名字若已被分类为局部但此刻未绑定，不会继续向外找 |
| E — Enclosing | 源码词法上一个或多个外层函数作用域 | 可以有零层或多层；不是运行时调用者的局部环境 |
| G — Global | 当前代码所属模块的全局命名空间 | 每个模块通常各有自己的全局命名空间，不是整个程序的共享名字池 |
| B — Builtins | 内置名字所在的命名空间 | 只有更近的适用层都未命中时才成为回退层 |

遮蔽只表示本次读取在更近层先找到了同名绑定；它不会删除、修改或搬走外层绑定。查找在首次命中后停止，也不会因为所得对象“不适合下一步操作”而继续向外试另一个同名对象：

```python
import builtins

len = "module shadow"

print(len)                         # module shadow
print(builtins.len(("a", "b")))  # 2
```

裸名字 `len` 在 G 层命中字符串后就结束；`builtins.len` 则先按普通名字规则解析模块名字 `builtins`，再对模块对象执行属性查找，并不是让裸 `len` 特殊地跳过遮蔽。`globals()` 中没有 `len` 也不妨碍裸名字最终到 B 层命中，因为 builtins 并没有被合并进模块全局字典。

判断路径时必须先画真实词法结构。一个直接定义在模块层的函数没有 enclosing 函数层，其未命中的局部读取路径是 `L → G → B`，不能写成“E 存在但未命中”。函数从哪里被调用也不会把调用者局部环境插入自己的作用域链；Python 在这里采用词法作用域，而不是动态作用域。

### 19.4 局部名字分类、运行期绑定与 `UnboundLocalError`

函数局部名字分类不是逐行临时决定的。若函数代码块中存在对简单名字的绑定操作，且没有相应 `global` 或 `nonlocal` 声明，该名字会在整个函数代码块中被视为局部名字。控制流只决定某次调用是否已经执行建立该绑定的语句，不会为每条路径重新分类名字。

```python
counter = 10
events = []

def update(flag):
    events.append(f"start:{flag}")
    before = counter
    if flag:
        counter = before + 1
    return counter
```

无论 `flag` 是 `False` 还是 `True`，函数体中的简单赋值都使 `counter` 成为该函数的局部名字。执行到 `before = counter` 时，右侧尝试读取尚未绑定的局部 `counter`，因此触发 `UnboundLocalError`；它不会回退到模块层的 `counter = 10`。

完整执行轨迹应写成：

```tex
进入 update 调用
→ append 已完成，events 已留下副作用
→ 进入赋值语句 before = counter
→ 求值右侧局部 counter 时失败
→ 左侧 before 的绑定未完成
→ 后续 if、return 完全未到达
→ 异常向外传播，但此前 append 不回滚
```

“语句已经开始执行”“右侧求值完成”“左侧绑定完成”是三个不同节点。阶段测验的一个轻微扣分正来自把已经进入、但在右侧失败的赋值语句整体列为“没有执行”。

分支也只改变运行期绑定状态：

```python
def select(flag):
    if flag:
        result = ["scan"]
    return result
```

`result` 对两条路径都是局部名字；真分支先建立绑定后正常返回，假分支读取尚未绑定的 local 时触发 `UnboundLocalError`。对象是否可变与这项分类无关。

简单名字的增强赋值也同时包含读取与把结果绑定回目标，因此 `counter += 1` 仍会影响 `counter` 的局部分类。它在绑定层面不同于 `events.append(...)`：后者先取得列表对象再调用方法，通常不重新绑定名字 `events`。不能因为某个 `+=` 可能调用对象的原地协议，就忽略其简单名字目标仍承担绑定操作。

### 19.5 `global` / `nonlocal`：绑定目标与词法边界

两种声明都作用于当前代码块中的相应名字，但目标不同：

| 声明 | 绑定操作的目标 | 不会做什么 |
| --- | --- | --- |
| `global name` | 当前代码所属模块的全局命名空间 | 不把对象变成“全局对象”，不修改其它模块的同名绑定 |
| `nonlocal name` | 词法上最近的已有外层函数绑定 | 不指向模块全局，不沿运行时调用栈任意寻找调用者 |

```python
mode = "scan"
events = []

def finish():
    global mode
    events.append(mode)
    mode = "done"
```

`events.append(mode)` 读取模块名字并修改已找到的列表对象，不需要 `global events`；`mode = "done"` 要重新绑定模块名字，因而使用 `global mode`。声明改变的是名字绑定目标，不改变字符串或列表的类型、身份和可变性。

对 `global` 还要保留一个读取精度：它不会立即创建模块绑定，主要改变简单名字的绑定和删除目标。读取显式 global 名字时按全局名字规则先查当前模块 G；若模块中没有同名绑定，仍可回退到 B。因此“声明了 `global len` 且模块没有 `len`”并不必然报错，它仍可能读到内置 `len`；只有适用的 G 与 B 都没有该名字时才是 `NameError`。

`nonlocal` 则用于改变 enclosing 绑定：

```python
def outer():
    label = "outer"
    events = []

    def change():
        nonlocal label
        events.append(label)
        label = "changed"

    change()
    return label, events
```

`label = "changed"` 重绑最近的外层函数名字，所以需要 `nonlocal label`；`events.append(label)` 只是修改外层名字所指列表，不需要 `nonlocal events`。若再包一层且近、远两层都有 `label`，`nonlocal label` 只选择最近的已有 enclosing 绑定，不能任意跳到更远层。

### 19.6 跨作用域重绑、共享对象修改与闭包入口

跨作用域状态题应先写“名字—对象”账本，再判断操作：

| 操作 | 名字绑定是否改变 | 对象是否可能改变 | 是否通常需要声明 |
| --- | --- | --- | --- |
| `records.append(x)` | 否 | 是，修改已找到的列表 | 不需要，仅先读取 `records` |
| `records[key] = value` | 基础名字不变 | 是，由下标协议修改对象 | 不需要重新声明基础名字 |
| `records = []` | 是 | 创建新列表，但旧列表本身不因此改变 | 目标为 G 时用 `global`；目标为 E 时用 `nonlocal` |
| `records += [x]` | 对简单名字包含绑定回目标 | 可能先执行原地协议，也可能得到新对象 | 必须按简单名字绑定目标判断，不能等同于 `append` |

多个名字可以引用同一个对象；通过任何别名完成原地修改，其它别名通常都能观察到。重新绑定其中一个名字只改变该绑定，不会自动同步其它别名。判断共享状态时必须说清共享的是哪个对象，还是哪个 enclosing / module 绑定。

闭包入口只保留最小模型：

```python
def make_state():
    state = []

    def read_state():
        return state

    return read_state, state

reader, external = make_state()
external.append("updated")
print(reader() is external)  # True
```

对 `read_state` 而言，`state` 不是 local，也不是模块 global，而是来自 enclosing 作用域的 free name。外层调用返回后，内部函数仍能访问执行所需的外层绑定；列表没有被闭包自动复制、浅拷贝或深拷贝，所以 `reader()` 与 `external` 观察同一对象。

若再次调用 `make_state()`，该例会建立新的内部函数对象、enclosing 绑定环境和新列表；两组状态相互独立。正式主线的结论只到“free name 能继续解析、共享对象身份可追踪”为止，不检查 cell、`__closure__`。阶段笔记后的 optional follow-up 只沉淀下列与 C17 直接相连的耐久边界；它们不计入完成分母，系统的循环闭包、回调与高阶组合仍留给 C19。

#### 可选 follow-up：跨调用状态的所有者与循环闭包晚绑定

“函数跨调用保留状态”的五种常见方式不是五种作用域，而是不同的长寿命状态所有者、访问协议和共享粒度：

| 状态载体 | 真正的状态所有者 | 共享与访问边界 |
| --- | --- | --- |
| 模块全局名字 | 已加载模块的命名空间 | 使用同一模块对象的代码通常共享；`global` 只让简单名字重绑写向本模块，修改已找到对象不因此需要声明 |
| 实例属性 | 具体实例对象 | `self.attr` 使用属性协议而不是新增 LEGB 层；通常按实例隔离，是否共享仍取决于属性是否指向同一对象 |
| enclosing / 闭包 | 某次外层工厂函数调用建立的绑定环境 | 同一环境中的闭包可以共享；重绑外层名字用 `nonlocal`，再次调用工厂通常建立新环境 |
| 参数默认值 | 创建函数对象时保存的默认对象 | 省略实参时，本次调用的局部形参绑定该对象；同一函数对象共享所保存的引用，可变对象修改会累积，调用者也能显式覆盖默认值 |
| 函数属性 | 具体函数对象 | `func.attr` 使用属性协议；同一函数对象的别名共享属性，它既不是调用局部命名空间，也不是 LEGB 的新层 |

这些方式默认只保留当前进程中的内存状态，不等于持久化，也不自动提供并发安全。一个主要行为加少量私有状态时，闭包通常简洁；状态扩展到多字段、多行为、不变量或明确生命周期时，实例属性能让所有权更显式。可变默认值与函数属性不宜被当作隐蔽业务状态，模块状态也只应承载真正需要模块级共享的内容。

循环中创建多个 `lambda` 或 `def` 时，每轮通常只是重新绑定同一个循环名字；不同函数对象若都引用该 binding，延迟调用时会读取它的当前值，因而常一起看到循环最终值。这是**词法作用域下 free name 的晚绑定**，不是动态作用域；**模块顶层循环也可能呈现相同结果**，但那里延迟读取的是 global，而非 enclosing binding。

`lambda x, i=i: i ** x` 中，右侧 `i` 在创建该函数对象时求值，左侧 `i` 是以后调用中的局部形参；它固定的是当时的对象引用，不复制可变对象内容，而且该参数仍可被调用者覆盖。工厂函数可通过每次调用建立独立 enclosing 绑定，`functools.partial` 可显式固定已有函数的实参；只在原循环作用域写 `saved = i` 或加入 `nonlocal` 都不会自动产生每轮独立绑定。完整参数规则留给 C18，系统的 lambda、回调与高阶函数设计留给 C19。

### 19.7 `locals()` / `globals()` 的有限观察与显式依赖

命名空间观察必须带上调用时刻和代码块类型。对当前 Python 3.14.5 的优化函数作用域：

- `locals()` 每次返回新的字典快照；其中不仅有调用点当前已绑定的函数局部变量，也有当前可用的外层绑定引用（文档术语为 nonlocal cell references）。静态上被分类为 local 但尚未建立运行期绑定的名字，仍不会因此出现在快照中。
- 保存下来的旧 `locals()` 字典不会因之后建立新局部绑定而自动更新；修改该字典也不是可靠写回真实局部变量的接口。
- 独立新快照是 Python 3.13+ 对优化作用域的明确合同；仓库旧 CPython 3.9.13 的对照探针会在同一帧复用并刷新同一映射。某个实验若每帧只调用一次 `locals()`，两版正文输出可能相同，不能据此证明返回映射的身份或刷新语义。
- `globals()` 返回当前代码所属模块的实际全局命名空间字典；直接修改它可以影响模块绑定，但这既不是动态作用域，也不应成为普通业务状态管理接口。
- `globals()` 不合并 builtins；模块字典中没有 `len`，不妨碍普通名字读取在 G 未命中后到 B 层命中。
- 命名空间映射只能证明观察时有哪些名字绑定，不能证明对象的创建地点、唯一引用或所谓“局部/全局归属”。

因此，在 `outer → middle → inner` 的嵌套探针中，`middle` 的快照出现 `x` 不表示 `x` 由 `middle` 拥有：它是为更深层 `inner` 传递的 free reference；保留 `print(y)` 时，`y` 也是 `middle` 的 free reference，注释该读取后便不再出现。`def inner` 尚未执行时，静态 local 名字 `inner` 还没有运行期绑定，所以不会进入该次快照；`inner` 中的 `y = 20` 始终建立自己的 local。以上观察不会改变 `nonlocal x` 仍以词法方式命中最近已有外层函数绑定的规则，也不应把当前 CPython 打印字典时的键顺序升级成 `locals()` 的跨实现合同。

工程上更好的默认路线，是让真正影响计算的依赖出现在调用点：

```python
DEFAULT_LOCALE = "en-US"

def build_label(key, locale):
    return {"key": key, "label": f"{locale}:{key}"}

selected_locale = DEFAULT_LOCALE
entry = build_label("menu.start", selected_locale)
events = []
events.append(f"built:{entry['key']}")
```

核心函数只读取显式参数并返回结构化结果；调用方选择默认值并拥有事件列表，配置选择、测试输入和副作用归属都清晰可见。模块常量并非天然错误：稳定、只读约定明确的默认值可以留在模块边界；真正需要警惕的是核心计算暗中依赖可变模块状态，或通过 `globals()` / `locals()` 把数据流藏起来。

返回表达式还提醒了一个名字边界：上例字典直接写在 `return` 中，它会被创建并交给调用者，却不必先绑定给函数局部名字。作用域分类适用于名字；对象不会因为在函数体求值过程中创建就获得“局部对象”属性。正常返回后，调用方名字 `entry` 才绑定返回的字典。

### 19.11 工程应知应会、习惯、禁忌和技巧清单

#### 读代码时

- 先画函数的源码嵌套树，再写实际存在的 L/E/G/B 路径；不要从调用栈反推词法作用域。
- 圈出简单名字的赋值、增强赋值和声明，先确定名字类别，再按控制流判断当前是否已经绑定。
- 对每个读取记录“在哪一层首次命中”；对每个赋值记录“哪个命名空间中的哪个名字被重绑”。
- 对方法调用、属性赋值和下标赋值，先写出基础名字解析到哪个对象，再判断对象是否被修改。
- 遇到异常，分别记录已经完成的副作用、尚未完成的目标绑定和完全未到达的后续语句。

#### 设计函数时

- 让影响计算结果的配置优先通过参数显式进入核心函数，让结构化结果通过返回值离开。
- 由调用方拥有日志、事件列表和边界 I/O；若核心函数确需修改共享对象，应在合同中明确对象身份和部分失败语义。
- 模块大写常量可以表达受控默认，但大写只是约定；不要把可变业务状态藏在模块名字或 `globals()` 中。
- 只有确实要重绑模块名字或最近 enclosing 名字时才分别使用 `global` / `nonlocal`，并让共享状态范围保持小而清楚。
- 当闭包状态开始包含多项数据、复杂转换或多个写入口时，应暂停比较显式对象或类设计；具体高级闭包设计留到后续章节。

#### 验证时

- 用 `is` 验证是否仍是同一对象，用 `==` 验证值是否相等；不要从值相等推断共享身份。
- 为局部分类、运行路径和对象变化分别设观察点，不用一次最终 `print` 包办全部证据。
- 只观察 `locals()` / `globals()` 中必要的键，记录调用位置和 Python 版本；不要打印整个命名空间制造噪声或泄露无关状态。
- 对全局重绑、外层重绑和共享对象修改分别构造最小探针，并同时检查旧别名是否仍指向旧对象。
- 把 `py_compile`、代表性运行和结构检查解释为各自有限的证据，不把它们升级成完整业务正确性证明。

#### 禁忌与可复用技巧

- 不说“局部对象”“全局对象”；应说哪个命名空间中的名字绑定到哪个对象。
- 不把 `UnboundLocalError` 简化为模块或 builtins 中没有同名名字。
- 不机械写满 LEGB 四层，也不把运行时调用者局部环境当成 E。
- 不把 `global` / `nonlocal` 当成通用报错补丁；使用声明等于选择了相应共享状态设计。
- 不用对象可变性决定名字作用域，也不把 `append()` 与简单名字 `+=` 的绑定语义混成一类。
- 不用 `locals()` / `globals()` 写回代替正常参数、返回值和状态对象。
- 可复用的审查表是：**词法树 / 名字类别 / 绑定目标 / 当前绑定状态 / 命中层 / 对象身份 / 修改或重绑 / 异常前效果**。

### 19.12 阶段精髓小结

```tex
名字的核心：名字只是标识符；对象没有由作用域赋予的“局部/全局”属性。
绑定的核心：绑定是某个命名空间中的“名字 → 对象”关系，不自动复制对象。
作用域的核心：作用域是源码中的词法可见区域；命名空间是运行时绑定环境。
读取的核心：裸名字沿实际存在的词法层级查找，并在第一个匹配绑定处停止。
局部的核心：函数代码块先分类名字；运行路径再决定该局部绑定此刻是否已建立。
报错的核心：读取尚未绑定的 local 触发 UnboundLocalError，不会退回模块同名绑定。
声明的核心：global 指向当前模块绑定，nonlocal 指向最近外层函数绑定；二者不改变对象。
状态的核心：修改已找到对象与重新绑定名字是两条路径，声明需求取决于绑定目标而非可变性。
闭包的核心：内部函数可在外层调用结束后继续访问所需 enclosing 绑定，不自动复制共享对象。
观察的核心：locals() / globals() 只能提供带版本、代码块和时点边界的命名空间证据。
工程的核心：让依赖通过参数进入，让结果通过返回值离开，让副作用所有权留在清晰边界。
证据的核心：每个结论都要同时说明命中层、对象身份、控制流阶段和不能推出的范围。
```
