在此首先引入一套可用于真实重构的方法：

> 在编写或拆分函数之前，先明确它接受什么、交付什么、改变什么，以及失败时留下什么。

考虑：

```python
def normalize_key(key):
    return key.strip().lower()
```

仅写：

```tex
把 key 规范化。
```

过于模糊，因为它没有说明：

- “规范化”究竟包含什么；
- 是否修改原对象；
- 是否可能返回 `None`；
- 是否进行文件写入；
- 空字符串是否合法；
- 输入必须是 `str`，还是只需支持相应操作。

更完整的契约卡可以是：

```tex
函数名：
    normalize_key

主要职责：
    去除键两端空白，并将其转换为小写形式。

输入：
    key：
        一个本地化键对象。

    最小运行接口：
        key 支持 strip()；
        strip() 的结果支持 lower()。

    项目业务限制：
        初步设计为接受 str。
        空字符串是否合法，应由原脚本业务规则确认。

正常返回：
    key.strip().lower() 的结果。

输入对象修改：
    当前实现不进行显式原地修改。
    对 str 输入不会修改原字符串。

显示输出：
    无。

日志：
    无。

外部 I/O：
    无。

消费行为：
    无一次性迭代消费。

异常：
    不兼容对象可能在 strip() 或 lower() 处失败；
    是否主动抛出业务异常，需要结合原脚本确认。

部分失败边界：
    当前函数没有先发生的外部副作用。

非职责：
    不校验键是否重复；
    不创建问题记录；
    不打印或保存报告。
```

再为 `extract_placeholders()` 建立初步契约。在没有原脚本之前，不能凭空确定它支持：

- Python `{name}` 占位符；
- printf `%s`；
- 游戏引擎专用标记；
- 转义规则；
- 嵌套格式；
- 重复占位符计数。

因此现在只能建立**结构契约**，不能擅自建立最终业务规则：

```tex
函数名：
    extract_placeholders

主要职责：
    从一段本地化文本中提取符合项目规则的占位符信息。

输入：
    text：
        待分析的文本。

    最小运行接口：
        取决于最终实现；
        若使用正则表达式，通常要求输入是 str 或兼容文本对象。

    项目业务限制：
        占位符语法和转义规则必须从原脚本确认。

正常返回：
    应返回一个可比较的数据对象。
    具体选择可能是 list、tuple、set、Counter 等，
    必须依据“顺序、重复次数是否重要”决定。

输入对象修改：
    不应修改输入文本。

显示输出：
    无。

日志：
    无。

外部 I/O：
    无。

消费行为：
    无外部迭代器消费。

异常：
    非法输入类型或实现所依赖操作产生的异常；
    是否把格式异常作为数据返回，需确认原业务规则。

部分失败边界：
    应尽量无外部副作用。

非职责：
    不负责比较源文与译文；
    不负责创建完整问题记录；
    不负责打印报告。
```

再为 `make_issue()` 建立契约。这个函数通常适合成为一个小型构造函数：

```python
def make_issue(code, message, *, entry_key=None):
    return {
        "code": code,
        "message": message,
        "entry_key": entry_key,
    }
```

这里只是结构示例，不代表原脚本最终字段。

契约卡：

```tex
函数名：
    make_issue

主要职责：
    按统一结构创建一条质量问题记录。

输入：
    code：
        问题代码。

    message：
        人读说明。

    entry_key：
        可选的相关条目标识。

    项目业务限制：
        字段名、是否允许 None、严重级别等需从原脚本确认。

正常返回：
    一个新的问题记录对象，初步考虑为 dict。

输入对象修改：
    不应修改传入对象。

显示输出：
    无。

日志：
    无。

外部 I/O：
    无。

消费行为：
    无。

异常：
    是否主动验证缺失字段，应依据项目合同决定。

部分失败边界：
    应无外部副作用。

非职责：
    不判断某项规则是否违规；
    不把问题追加到全局列表；
    不打印问题；
    不保存报告。
```

再为 `build_entries()` 建立契约。`build_entries()` 很可能负责把原始输入转换为统一的内部记录。

初步契约：

```tex
函数名：
    build_entries

主要职责：
    将原始输入记录转换为质量门禁使用的统一条目结构。

输入：
    raw_records：
        可迭代的原始记录。

    最小运行接口：
        raw_records 可迭代；
        每个原始记录支持当前实现需要的字段读取操作。

    项目业务限制：
        原始记录字段、缺失字段处理、字段默认值、
        顺序规则和重复记录规则必须从原脚本确认。

正常返回：
    一个新的条目集合；
    初步可能为 list[dict[...]]。

输入对象修改：
    原则上不修改原始记录；
    是否复制嵌套对象必须按实现确认。

显示输出：
    无。

日志：
    无或仅在明确设计时记录诊断信息。

外部 I/O：
    不应负责读取源文件；
    应接收已经解析的记录。

消费行为：
    通常完整遍历 raw_records 一次；
    若输入是迭代器，会推进或耗尽它。

异常：
    记录形状不兼容、缺少必需字段、
    字段转换失败等异常。

部分失败边界：
    若采用逐步构建局部列表，异常前已构建的局部结果
    通常不会交付给调用者，除非函数修改外部列表。

非职责：
    不打印最终报告；
    不写 JSON 文件；
    不负责所有质量规则验证。
```

再为 `validate_entries()` 建立契约。这是门禁脚本中最可能承载核心业务规则的函数。

初步契约：

```tex
函数名：
    validate_entries

主要职责：
    对统一条目集合执行项目规定的质量规则，
    并收集结构化问题记录。

输入：
    entries：
        可迭代的统一条目。

    最小运行接口：
        entries 可迭代；
        每个 entry 支持规则所需的字段读取操作。

    项目业务限制：
        必须从原脚本确认全部规则、执行顺序、
        重复问题处理方式和严重级别。

正常返回：
    一个新的问题集合，初步可能为 list[dict[...]]；
    或返回包含统计信息的报告对象。

输入对象修改：
    原则上不修改 entries；
    必须通过源码确认。

显示输出：
    不应直接打印最终报告。

日志：
    可选；若存在，需要明确级别和内容。

外部 I/O：
    不应直接保存报告文件。

消费行为：
    至少完整遍历 entries；
    若多条规则分别遍历，可能要求可重复迭代，
    或需先物化为列表。

异常：
    条目结构错误；
    规则处理中的异常；
    是否将部分输入错误转为问题记录需按业务确认。

部分失败边界：
    若返回局部列表且不修改外部状态，
    异常时通常不会交付不完整结果；
    若直接追加到调用者列表，可能留下部分问题。

非职责：
    不负责人读格式排版；
    不负责文件持久化；
    不负责命令行退出。
```

再为 `print_report()` 建立契约：

```tex
函数名：
    print_report

主要职责：
    将结构化报告转换为人读文本并写入指定文本流。

输入：
    report：
        结构化报告对象。

    stream：
        可选文本输出流；
        若未显式提供，可能使用标准输出。

    最小运行接口：
        report 支持所需字段读取；
        stream 支持 write()，或使用 print(..., file=stream)。

正常返回：
    通常为 None。

输入对象修改：
    不应修改 report。

显示输出：
    是；
    输出格式、排序、换行和编码边界需明确。

日志：
    通常无。

外部 I/O：
    向文本流写入；
    若使用标准输出，属于进程输出副作用。

消费行为：
    若 report 中包含迭代器，打印过程可能消费它；
    更稳妥的报告对象通常应已物化。

异常：
    缺失字段、格式转换错误、输出流写入失败等。

部分失败边界：
    输出过程中失败时，目标流可能已经包含部分文本。

非职责：
    不重新执行质量验证；
    不改变报告内容；
    不保存 JSON 数据文件。
```

再为 `save_report()` 建立契约：

```tex
函数名：
    save_report

主要职责：
    将结构化报告以规定格式持久化到目标位置。

输入：
    report：
        结构化报告对象。

    path：
        目标路径。

    最小运行接口：
        path 可被 Path 接受，或提供项目规定的路径接口；
        report 可被目标序列化器处理。

    项目业务限制：
        文件格式、编码、换行、缩进、是否覆盖、
        原子写入及目录创建规则必须从原脚本确认。

正常返回：
    可以返回最终 Path、写入字符数或 None；
    必须选择并稳定下来。

输入对象修改：
    不应修改 report。

显示输出：
    原则上无；
    成功提示应由调用层或 print_report() 负责。

日志：
    可选。

外部 I/O：
    创建或覆盖目标文件并写入内容。

消费行为：
    序列化可能遍历 report 内部容器。

异常：
    序列化失败、目录不存在、权限不足、
    磁盘或路径错误等。

部分失败边界：
    普通覆盖写入失败时可能留下空文件或部分文件；
    若要求原子替换，需要专门实现和验证。

非职责：
    不执行质量验证；
    不决定报告业务内容；
    不把保存成功等同于报告通过。
```
